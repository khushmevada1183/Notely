# Notely Idle Memory Cleanup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reduce Notely's idle memory footprint from the reported ~500 MB by removing runtime registrations, startup processes, source artifacts, and npm dependencies that are not required by the minimal editor experience, with measured before/after evidence.

**Architecture:** Keep Notely as a focused VS Code workbench slice. Remove services at their entry-point import/registration boundary, use existing null services where a retained MainThread requires an interface, and keep the update service, editor/file I/O, themes, find/replace, accessibility basics, and allowlisted grammar extensions. Treat npm cleanup separately from runtime cleanup: prove each top-level package is unused by source, build, test, and packaging scans before removing it from `package.json`, then regenerate `package-lock.json`.

**Tech Stack:** TypeScript, Electron 42, Node.js 24.18.0, npm lockfile v3, VS Code gulp build, Bash, Linux `/proc` memory counters.

**Spec:** `README-NOTELY.md`, current Notely production-trim guidance in `.agents/skills/notely-production-trim/SKILL.md`, and the measured audit produced by Task 1.

## Global Constraints

- Node.js requirement remains **24.18.0** as documented in `README-NOTELY.md`.
- Notely keeps update UI and auto-update wiring: retain `updateService.js` and `update.contribution.js`.
- Notely keeps real workbench editor, file I/O, themes, and find/replace; do not replace them with a standalone Monaco implementation.
- Notely does not load SCM, terminal, chat, MCP, remote development, sync, marketplace/recommendation, or agent-host features.
- Do not delete upstream `src/vs/workbench/contrib/chat` or remove AI packages from the root manifest until source/build/test evidence proves the root dependency is unused by all required targets.
- Do not alter unrelated user changes in the worktree.
- Every deletion batch must leave a focused executable check and a rollback point.
- Memory comparisons use the same Linux host, Electron build, profile flags, input file, and extension settings; report RSS and PSS separately.

## Audit File Map

- `scripts/notely-memory-audit.sh`: reproducible cold-start and idle process-tree memory measurement; emits JSON/TSV suitable for comparing commits.
- `scripts/notely-perf-startup.sh`: existing startup benchmark; extend only where needed to make readiness and process cleanup reliable.
- `src/vs/workbench/workbench.minimal.main.ts`: renderer/workbench service and contribution imports; remove runtime feature registrations here.
- `src/vs/workbench/workbench.desktop.main.ts`: desktop service and contribution imports; remove desktop-only services here while preserving file dialogs, lifecycle, update, URL, title, native host, clipboard, and extension management required by Notely.
- `src/vs/workbench/contrib/minimalEditor/browser/minimalExtensionHostServices.contribution.ts`: minimal extension-host service registrations and MainThread contributions; keep only APIs needed by allowlisted extensions.
- `src/vs/workbench/api/browser/extensionHost.minimal.contribution.ts`: minimal extension-host contribution entry point; verify it does not transitively restore removed chat/git/terminal/notebook RPCs.
- `src/vs/code/electron-main/app.ts`: process spawning and app-level startup decisions; retain the existing Notely guard and remove any remaining Notely-only child-process startup that the audit identifies.
- `build/lib/notelyDirs.ts`: Notely npm roots, extension compilation list, desktop entry exclusions, and TypeScript exclusions.
- `build/npm/dirs.ts`: postinstall directory selection; keep it aligned with `getNotelyNpmDirs()`.
- `build/gulpfile.extensions.ts`: Notely extension compilation selection.
- `build/lib/notelyPackage.ts`: installer-only npm and compiled-output exclusions.
- `build/.moduleignore.notely`: installer-only module exclusions.
- `scripts/notely-trim-extensions.sh` and `scripts/notely-trim-sources.sh`: destructive source/worktree cleanup scripts; make them idempotent and evidence-driven before using them.
- `package.json`: remove only proven-unused root entries and Notely-inapplicable compile/watch scripts; preserve packages needed by upstream build/test targets unless the repository explicitly defines a Notely-only install manifest.
- `package-lock.json`: regenerated by npm after manifest changes; never hand-edit dependency resolution entries.
- `README-NOTELY.md`: document the audit command, memory metrics, preserved services, and validation commands.

### Task 1: Establish a Reproducible Idle-Memory Baseline

Expected: FAIL because the audit script does not yet exist.

- [ ] **Step 3: Implement the smallest reproducible measurement**

Launch Notely with a temporary user-data directory, `--disable-extensions`, `/tmp` as the input, and the same readiness detection used by `scripts/notely-perf-startup.sh`. Read `VmRSS` from `/proc/<pid>/status`, read `Pss` from `/proc/<pid>/smaps_rollup` when available, sum each process once, emit the process table and totals, and always kill/wait/remove the temporary profile through a trap. - [ ] **Step 4: Run the audit and save the baseline**

Run five cold starts with the same command and record median/min/max total RSS and PSS, process count, readiness time, and the largest child processes. Run: `for i in 1 2 3 4 5; do NOTELY_AUDIT_SECONDS=10 ./scripts/notely-memory-audit.sh; done`

Expected: five complete records identifying whether the ~500 MB is in the browser/renderer, shared process, extension host, GPU, or another child.

- [ ] **Step 5: Document the baseline and invariants**

- [ ] **Step 6: Run the focused validation**

Run: `bash -n scripts/notely-memory-audit.sh && ./scripts/notely-memory-audit.sh --self-check`

Expected: PASS, followed by a clean startup/idle sample when run without `--self-check`.

- [ ] **Step 7: Commit the independently testable baseline**

